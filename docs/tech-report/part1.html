01项目概述Overview

1.1问题：政策文本与「我能不能申」之间的缺口

学生资助、专项补贴、推免保研、基层就业代偿这类政策，几乎都有一个共同形态：一份上万字的公文，加上若干个附件， 真正的资格条件散落在条文、括号、脚注和「原则上」「一般应」这类弹性表述里。本项目收录的 32 份国家级政策， 原文合计 10.2 万字，被拆出 339 条可判定条件——平均每份政策 10.6 条，最多的《事实无人抚养儿童保障意见》有 23 条。

而用户的问题只有一个：「我这种情况，到底能不能申？」现行的解决方式都不理想：逐份读原文（读完仍不确定自己算不算 「家庭经济困难」）、问辅导员和学长（口径因人而异）、直接去资助中心（跑了才知道缺材料）。信息不对称的成本，最终由 最不熟悉流程的那部分学生承担。

痛点政策文本不是给人「算」的

同一件事有 285 种字段写法：education.level、student.educationLevel、 education.stage、school.type……跨政策复用极少，最高频的学历字段也只出现在 7 份政策里。 逐份填一遍，等于把同一份简历抄 32 次。

机会把「读」变成「算」

政策条文一旦被拆成「字段 + 操作符 + 阈值」的结构化条件，就可以像代码一样被逐条求值：给一份用户画像， 引擎输出每条条件是符合、不符合还是待补充，并给出原文出处。判定这件事，本就不该交给概率模型。

1.2产品定位：不是政策问答，是资格判定

市面上同类工具大多是「政策问答机器人」或「办事清单助手」：前者回答「政策说了什么」，后者列出「要准备什么」。 它们都停在信息整理这一层，没有回答最关键的那一步——以你个人的情况去逐条比对，你到底卡在哪一条。 本项目的差异点集中在三件事上：

维度常见做法能申吗的做法
输出结论生成一段回答或一份清单，由用户自己对照 逐条给出「符合 / 不符合 / 待补充 + 建议」，并汇总为一句人话结论（可申 / 暂不符合 / 还不能下结论）
结论依据模型生成，无法验证，可能编造 每条条件绑定 docRef 与原文 quote，页面可点回原文段落并高亮原句；测试断言引文 100% 可在原文中逐字定位
运行成本每次提问调用大模型，结果不稳定、有 token 成本 大模型只在开发期「建库」用一次；用户每次判定都是本地确定性引擎，零 token、断网可跑、结果可复现

1.3功能全景

产品把「贴政策 → 判自己」拆成六个可验证的步骤。前四步发生在开发期与入库期，后两步是用户每次使用都会走的链路：

01政策入库从教育部、全国学生资助管理中心等官网抓取原文，逐字存档不加工人工 + 脚本data/policies/raw/*.txt
02AI 抽条件DeepSeek 把原文抽成「条件组 / 条件 / 字段 / 材料 / 时间节点」的 JSON 条件树DeepSeek deepseek-chatdata/policies/*.json + docs/ai-log/
03人工复核逐条核对条款、引用、判定口径，修正模型输出的分类与逻辑错误，过时条款写进 notes团队（57 条复核记录）review.changes[]
04填自己表单字段由政策动态生成，只问这份政策真正用得上的信息；留空不算不符合用户/match/:id
05本地判定规则引擎在服务端（或浏览器内）逐条求值，输出四类状态与汇总结论判定引擎matcher.ts / evaluate()
06回溯原文每条结论可点回原文段落，命中的句子高亮；附材料清单与时间节点用户判定报告 + 政策原文标签页

表 1-1　六步链路：前四步保证「条件是对的」，后两步保证「结论是可查的」。

围绕这条主链路，系统还长出了四个横向能力，解决主链路之外的三个问题：不知道该看哪份（政策雷达：26 项画像横向判定 32 份）、 不知道什么时候申（年度申报日历：60 个时间节点按月摊开）、想把条件看明白再填（政策详情页：条件树 / 材料 / 时间节点 / 原文一页读完）、 想换设备接着填（账号体系与个人中心）。

1.4一个真实的使用场景

场景大二学生小李，想知道自己能申哪些钱

她打开政策库，32 份政策一眼望不到底。于是点开政策雷达，只填了 19 项共性信息（学历层次、年级、入学年份、学校类型、 成绩排名、家庭是否困难……）。页面当场给出分层结论：4 份初筛适合、11 份差几项、2 份信息不够、15 份不符。

她点进「国家奖学金」，判定页已经从画像带入了 8 项信息（可改），剩下的几项按提示补上。点「开始判定」， 13 条条件逐条列出：11 条符合、2 条待补充，并明确写出「成绩排名前 10% 属于常规通道；若排名在前 10%–30% 之间， 需要同时提供其他方面表现特别突出的证明材料」——这句话直接对应原文第七条（二）。

她顺手点开申报日历：10 月有 4 个节点，其中「学生向学校提出申请」标着「个人要办」。整个流程没有一个字是模型现编的。

1.5文档结构

本文档按「问题 → 架构 → 流程 → AI → 数据 → 引擎 → 界面 → 质量 → 演进 → 缺陷 → 边界」组织。 其中第九章（重大版本更新）与第十章（缺陷修复记录）是本文档的重点：它们记录了项目从空仓库到当前版本的全部关键决策， 包括三次判断失误与一次整体回滚。系统如何工作是前八章的内容，它为什么会变成现在这样是后三章的内容——后者同样重要， 因为一个 32 份政策、339 条条件的判定系统，真正的风险从来不在代码写不出来，而在「判定口径悄悄错了却没人发现」。
