11.1已知边界

边界具体表现为什么现在这样
只覆盖国家级政策32 份均为全国性文件；省市级实施细则、校级评审办法不在库内 地方文件数量级大、时效差异大、格式更不规范；先把「全国通用骨架」跑通再谈扩展
政策会过期库内文件年份跨 2005–2025，部分额度与范围已被新文件替代 已在 notes 标注【现行标准】并在判定页展示；但无法保证实时同步官方更新
静态版无账号gh-pages 上不能注册登录，判定记录与进度不跨设备 静态站没有服务端；演示与真机使用走同一套判定引擎，仅账号能力缺失

数据存储为单机 JSON账号与用户数据存在 data/*.json，无数据库、无并发控制 面向演示与本机使用，量级在百人内足够；换成 SQLite/Postgres 是明确的后续项
无端到端自动化测试页面交互依赖人工验收清单 判定正确性由领域层单测覆盖，E2E 收益低；若后续页面复杂化再引入 Playwright

  • 时间解析（parseDeadlineText）基于正则规则，能覆盖「每年 X 月 X 日前」「X 月底」「X-X 月」「每学年」等常见表述， 但遇到「以当年通知为准」「9—10 月」这类模糊表述归入「其他流程节点」，不做硬解析——这是有意的保守处理。
  • 界面文案中仍有少量「大概率可以申」等口语化措辞，属于产品语气选择，但需在文档中明确其非承诺属性。

11.4结语

它把「读政策」这件需要经验和耐心的事，拆成了「AI 编译 + 规则判定 + 原文回链」三段，并让每一段都可检查。

对用户，价值是具体的：填一次表，看到自己与目标政策的差距在哪、还缺什么材料、下个月该做什么；每一条结论都能点开原文自己核对。

本项目在工程上的判断包括：把大模型限制在建库阶段、用 57 条记录做人工复核、一次修复后回查 32 份政策、功能改坏时选择回滚。这些选择都写在提交历史与本文档里。
