02系统架构Architecture

一句话概括架构：大模型只在开发期出现一次，把「自然语言政策」编译成「结构化条件树」； 运行期是一套纯函数规则引擎，同一份代码既跑在 Node 服务端，也直接打包进浏览器。 这个选择决定了整个系统的成本结构、可测试性与可解释性。

2.1总体架构

架构可以分成三条独立的链路，它们之间只通过文件与 HTTP JSON 耦合：

① 建库链路（开发期）

抓取原文 → 清洗噪声 → DeepSeek 抽取 → 结构校验/重试 → 人工复核 → 提交入库。 产物是 data/policies/*.json，随仓库走版本控制。

② 判定链路（运行期）

页面拉取政策 JSON，动态生成表单；用户填表后调用 evaluate()， 纯函数返回逐条结论。全程无网络、无模型、无密钥。

③ 账号链路（可选）

只用于跨设备保存「判定记录」与「填到第几项」，不保存填报内容本身。 静态部署模式下整条链路不启用。

三条链路里，只有 ① 需要 DEEPSEEK_API_KEY，而它永远不在运行期被调用。 这一点在代码里有硬约束：前端不携带、也不请求任何模型密钥；服务端除抽取脚本外没有任何 AI SDK 依赖。

2.4两种部署形态：同一套引擎，两个宿主

纯函数引擎带来一个直接好处：它不需要服务端也能跑。前端在 vite.config.ts 里把 @domain 别名指向 server/src/domain，静态构建时这套领域代码被打进浏览器 bundle；服务端模式则通过 HTTP 调用。 两条路径的判定结果逐字段一致——因为执行的是同一份源码。

能力服务端模式（pnpm dev / 自建服务器）静态模式（GitHub Pages）
政策数据Express 读 data/policies/*.json，GET /api/policies构建期导出成静态 JSON，浏览器 fetch
判定执行服务端 POST /api/policies/:id/evaluate浏览器内直接调用 evaluate()
政策雷达 / 日历GET /api/radar、GET /api/calendar（服务端现算）预先导出的 radar.json、calendar.json
账号与判定记录✅ 注册登录、跨设备记录、填报进度❌ 无账号体系（其余功能完全一致）
密钥仅建库脚本需要完全不需要
设计取舍为什么用「导出静态数据」而不是在浏览器里重新实现一遍逻辑

重写一遍意味着两份实现、两套 bug。这里的做法是把同一份领域代码搬进浏览器：matcher.ts、 radar.ts、calendar.ts 都是无 Node 依赖的纯 TS，@domain 别名一行配置即可复用。 代价是静态构建要显式导出数据（export-static-data.mjs），换来的是「判定行为只有一份定义」。

03核心流程与时序Flow & Sequence

这一章回答三个问题：一份政策是怎么变成可判定的 JSON 的（建库时序）、 一个用户点「开始判定」之后发生了什么（判定时序）、单条条件和一个条件组是怎么得出结论的（状态机）。

3.1建库链路：一份政策的完整生命周期

建库链路由 6 个脚本串成，每一步都留下可复核的产物：

脚本行数职责与关键约束
clean-policies.mjs162截掉网页导航与页脚噪声，按固定正文起点重算段落偏移；正文条款一字不改
extract-policies.mjs314调用 DeepSeek 抽取条件树；结构校验不通过则带错误重试一次；请求/响应写入 ai-log
repair-sections.mjs92修复段落切分与偏移（模型摘出的引文必须能在原文中定位）
fix-offsets.mjs57归一化定位：把 start/end 偏移重算成可稳定复现的位置
apply-review.mjs149把人工复核结论（改分类、调硬性、补 notes、删过时条款）批量落到 JSON，并写回 review.changes
export-static-data.mjs94导出 index.json / radar.json / calendar.json 供静态部署使用

3.2判定时序：从点下按钮到看见结论

一次判定在服务端模式下涉及 4 个参与者、6 次交互。注意两点：判定请求体只带画像、不带政策 （政策由服务端从已入库 JSON 读取，避免前端篡改数据）；返回值包含全部证据链（每条条件的 quote、docRef、 gap、hint），前端只负责渲染，不做任何判定逻辑。

步交互数据形态
1进入 /match/:id路由参数 id；页面并发拉取政策全量 JSON 与当前画像草稿
2动态渲染表单按 policy.fields[] 生成字段，按 lib/field-groups.ts 的语义分组折叠
3用户填表画像为扁平的 Record<string, unknown>，键是 education.grade 这类点路径
4点击「开始判定」POST /api/policies/:id/evaluate，body = { profile }
5引擎求值evaluate(policy, profile)：逐组求值 → 通道裁决 → 汇总 → 生成 headline / 材料清单 / 下一步
6渲染报告状态色块 + 逐条卡片 + 原文标签页；每条卡片可跳原文并高亮 quote

3.3单条条件与条件组：四种状态与两种合并规则

判定引擎只产出四种状态，含义被严格定义——用户最容易被误伤的，就是「没填」被当成「不符合」：

状态标记含义参与汇总结论
pass符合用户填的值满足该条件✅
fail不符合用户填的值明确不满足（且该条件是硬性）✅
unknown待补充字段没填 / 值无法与政策选项对齐 —— 不知道，不等于不符合✅（作为「还不能下结论」的依据）
warn建议项非硬性条件不满足，只提示不影响结论❌

合并规则按条件组的 logic 分两种，另有两条兜底：

规则合并逻辑

all（全部满足）：出现 fail → 组 fail；否则出现 unknown → 组 unknown；否则 pass。
any（满足任一）：出现 pass → 组 pass；否则全为 fail → 组 fail；否则 unknown。
兜底 1：any 组内条件全是建议项（required:false）时，不把整组判为 fail —— 否则「择优参考」会把用户误判成不符合（提交 5c4a0a6）。
兜底 2：配置了并列通道的政策，先按通道分组裁决，任一通道 pass 即整体 pass；通道之外的条件组仍需全部满足。

最终 headline 由 buildHeadline() 生成，只有三种口吻，且都带前提说明：「大概率可以申」（硬性条件全 pass）、 「暂不符合」（存在硬性条件 fail）、「还不能下结论」（存在待补充）。判定报告页尾部固定一行提示： 结论只反映你填写的信息，最终是否通过仍以学校、主管部门审核为准。

3.4横向能力：政策雷达与申报日历

政策雷达：一次画像，32 份分层

32 份政策共 333 个表单字段、285 种写法，逐份填不现实。雷达只问 26 项跨政策复用的信息， 用规则表把它们映射到每份政策自己的字段 key 上，再逐份调用同一个 evaluate()：

  1. 槽位定义：26 项 RADAR_SLOTS，带 aliases（同一件事的不同叫法）
  2. 字段映射：FIELD_RULES 把槽位值翻译成政策字段 key；映射不上宁可不写
  3. 逐份判定：调用 matcher.evaluate，与单政策页完全同源
  4. 四层分层：初筛适合 / 差几项 / 信息不够 / 不符

申报日历：60 个节点按月份摊开

原文里的时间表述是自然语言（「每年 10 月 31 日前」「6 月底」「入学后两周内」）， parseDeadlineText() 把它们解析成可排序的结构：

  1. 解析：年度周期 / 具体日期 / 学期节点 / 办理时限 / 政策沿革 / 其他
  2. 归月：能落月的进 12 个月份格，落不进的单独归类
  3. 责任方：按主语 + 动作判断「个人要办 / 学校院系 / 主管部门」
  4. 时效：往年一次性节点不混进今年待办，单独折叠为「政策沿革」

3.5失败路径与降级

失败场景系统行为设计理由
政策数据加载失败页面显示可读错误，不阻塞其他路由静态部署下单个 JSON 404 不应让整站白屏
画像字段未填判为 unknown（待补充），不算不符合漏填被当成不符合，会让用户放弃本来能申的项目
画像值与政策选项对不上字段标「请选择」并为空 → unknown；雷达映射不上则跳过该项写错比留空伤害更大
模型输出结构不合法建库期校验失败 → 带错误重试一次；仍失败则该政策不入库宁缺毋滥：坏数据入库比少一份政策更糟
服务端不可用账号相关功能降级；判定可切静态模式继续用答辩/评审现场网络不可控
