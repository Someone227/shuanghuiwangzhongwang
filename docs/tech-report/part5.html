深度剖析为什么「逻辑组合」是这类系统最大的风险

D-04 与 D-05 是同一类错误的两个变体：单条条件都忠实于原文，组合方式却错了。模型被要求「逐条抽条件」， 它确实做到了；但「这些条件之间是且还是或」需要理解整体语义，而这恰恰是提示词最难约束的部分。

更麻烦的是，这类错误在数据层面完全合法：JSON 结构正确、docRef 有效、quote 可回溯、测试全绿。它只会在「拿一个真实的人去跑一遍」时暴露。 这就是为什么项目必须做两件看起来「笨」的事：每份政策抽完人读一遍原文；每个里程碑用真实场景点一遍全流程。 目前 3 份政策、6 条通道的并列结构，全部来自这种人工核对。

10.5修复方法论：四步闭环

22 个缺陷（D-01 ~ D-22）不是随机修的，整个过程收敛成一套固定动作：

① 用真实场景复现

每条缺陷都对应一个具体的「用户路径 + 输入 + 错误输出」， 例如「本科二年级、排名 5%，国奖被判定不符合」。复现不出来的一律不当作缺陷处理。

② 定位到领域层还是展示层：先确认是引擎算错，还是页面显示错。前者必须补单测，后者必须收敛到统一的格式化函数。

③ 修复 + 补测试 + 数据检查

代码修完后，回头检查已有 32 份政策是否都受同一问题影响——D-04 修复时就顺带发现了中职国奖与少数民族骨干计划两处同类问题。

④ 记录成文档：每个缺陷的根因写进提交正文与本文档，避免「同样的错换个地方再犯」。回滚也走同样的流程（revert + diff 验证 + 重新部署）。
