07产品页面与视觉体系Product & UI

这个项目要回答的问题是「我能不能申、还差什么、什么时候申」，所以界面结构不是按技术模块切，而是按用户的一次完整决策过程切： 先横向摸底，再纵向核对，最后落到材料与时间。

7.2三条主线的页面配合

横向：先看我适合什么

首页 → 政策雷达。用户只填 26 项共性信息，一次拿到 32 份政策的粗分类， 再点进「去核对材料」进入具体政策。解决「不知道从哪份看起」。

纵向：我到底够不够格

政策库 → 判定页。表单字段由政策动态生成，只问这份政策真正用得到的； 提交后左侧表单/右侧结论双栏对照，每条结论可回链原文段落。

时间：什么时候动手

申报日历。把 32 份政策里的 60 个节点摊进一年 12 个月， 标出责任方与「往年一次性节点」，避免用户把学校流程当成自己要办的事。

三个入口共享同一份政策数据与同一套判定引擎，但页面职责严格分开：雷达不做精细判定，判定页不做时间规划，日历不做资格判断。 这样每个页面都只有一个主角，不会互相稀释。

7.4双主题：一套语义 token，两个色板

早期版本把颜色写死在组件里，改深色主题时要逐个页面改 bg-white/text-slate-900，漏改就会出现「深色页面里一块白卡」。 后来统一改成只用语义类名：组件写 bg-surface/text-ink/border-line/text-on-brand， 颜色值集中在 CSS 变量里，切换主题只换变量。

表 7-3　两套色板共享同一套语义 token。主题偏好存在 localStorage，首屏由 theme.ts（52 行）在挂载前同步 <html class="dark">，避免闪烁。

设计取舍为什么保留两套主题，而不是只做一套

深色不是「好看」，而是这个产品的场景需要：这类用户常常在晚上、在手机上翻政策。深色主题同时是一次工程约束的检验—— 只有当所有颜色都收敛到语义 token 时，才可能一键切换且不漏底色。事实上第一次做深色主题时，登录页的 tab 高亮用的还是裸颜色， 切到深色后立刻露白，这个缺陷记录在 10.2。

7.5响应式、可达性与打印

  • 布局：判定页在 ≥1024px 为「表单 380px + 结论自适应」双栏，<1024px 折叠为单栏并允许在「表单/结论」间切换，避免手机上表单过长。
  • 表格与卡片：政策卡片用 grid 自适应列数（1/2/3），徽章行允许换行——窄屏下曾出现徽章被挤断行，已改为 flex-wrap 修正。
  • 键盘：判定页支持 Ctrl + Enter 直接判定；表单控件均为原生 input/select，默认支持 Tab 与屏幕阅读器。
  • 空态与提示：任何空列表（无判定记录、无筛选结果、月份无节点）都有明确文案与下一步按钮，不留空白页。
  • 打印：结论区使用 @media print 去掉导航与按钮，A4 单栏输出，方便学生打印带去资助中心。

08质量保障与工程实践Quality & Engineering

这个项目最怕的不是页面难看，而是结论错了但看起来很对。所以质量保障的重心不在 UI 测试，而在两个地方： 判定引擎的单元测试，以及「数据与原文是否对得上」的契约测试。

8.1测试分层：9 个文件 / 79 个用例

测试用 Node 原生 test runner（tsx --test）运行，不引入 Jest/Vitest，启动快、无额外配置。9 个文件的分布刻意按「一个失败模式一个文件」组织：

8.2契约测试：把「AI 可能错」变成「结构必须对」

policies.test.ts 是整套测试里最特别的一个：它不测函数，只测数据本身。断言项包括：

结构与引用完整性

  • 每份政策 9 个必填字段齐全，level/category 在枚举内
  • 每条条件的 docRef 必须能在 sections[] 中找到
  • 公式里的字段路径必须在 fields[] 中声明
  • channels[].groupIds 引用的条件组必须真实存在
  • 材料、时间节点、条件三者之间不允许出现悬空引用

原文可回溯

  • 每条条件的 quote 必须是 originalText 的连续子串（逐字，非模糊匹配）
  • 段落偏移 start/end 必须与原文切片一致
  • 清洗后的原文不得为空，且长度在合理区间
  • 每份政策必须有 review.humanReviewed = true

第二条是关键：一旦模型「改了原话」或人工复核手抖改了引文，测试立刻失败。这把「AI 不编造」从提示词层面的期望，变成了构建时必须通过的硬校验。

两个 tools/*.mjs 的存在有特殊背景：本机 git push 与 git fetch 走网络经常被中断（详见第九章 9.6）， 最终改用 GitHub Git Data API 直接创建 commit 与 tree，再由本地精确重建 commit 对象对齐 SHA。这是被工程约束逼出来的方案， 但也带来一个额外好处：发布脚本可以精确控制「哪些文件进 gh-pages」，不需要维护额外分支的工作区。

8.4验收方式：每个里程碑都在浏览器里点过

本项目没有引入 E2E 测试框架（成本与收益不匹配：页面逻辑大多由纯函数驱动，E2E 覆盖不住判定正确性）， 但每个功能里程碑都执行同一套人工验收清单：

  • 走通主链路：从首页 → 选政策 → 填表 → 判定 → 看原文 → 回列表，全程无报错、无空白。
  • 边界场景：全空表单提交、只填一项、全部填「否」、数值填 0 与极大值、中文与符号混输。
  • 静态版与在线版分别验：静态模式 VITE_STATIC_DATA=true 走浏览器内判定；在线模式走 /api/policies/:id/evaluate。两者结论必须一致。
  • 部署后回访：gh-pages 发布后验证深链（直接打开 /match/national-scholarship）与资源 200。

8.5版本管理与协作约定

仓库根目录的 AGENTS.md 写死了三条铁律，整个开发过程按它执行：

① 重大更改必提交

新功能跑通、依赖/架构/数据模型变更、主流程 bug 修复、视觉或部署大改 → 必须 commit 并同步 GitHub。 文案与样式微调不算重大，可合并提交。

② main 永远可运行

任何提交后 main 都必须能起服务、能通过测试；大改走 feat/xxx 分支，验证通过再合并。

③ 细粒度历史

一次提交只做一件事，提交信息用 feat/fix/docs/style/refactor/test/chore 前缀 + 一句中文说明。 比赛的评审会看提交历史，一次性提交全部功能会被判为开发过程不可信。

实际执行结果：一次提交只做一件事，最大单次改动是「政策库扩充到 31 份」（新增 19 份政策数据），其余每次改动都能对应回一个具体问题或一个页面。 每个里程碑打一个 tag，回档时 git reset --hard <tag> 即可恢复可用状态——这也是用户明确要求的能力：「不要让网页因为乱改崩溃还没有办法回档」。
